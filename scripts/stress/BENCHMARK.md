# Fuzzy: решение после замеров

Выбран **общий Rust matcher**. Причина — независимое тестирование и читаемость алгоритма, единые scoring/ranking для двух входных сценариев и меньший пик памяти на измеренном наборе. DuckDB сохраняется как движок чтения входных query и вычислений pipeline.

**Rust не оказался быстрее DuckDB на 100K.** На плотных названиях он примерно в 2.4 раза медленнее. В абсолютных величинах 100K предложений получаются примерно за 3.5с; это принятый компромисс, а не заявление о превосходстве Rust по скорости. Однозначный набор — около 0.58с против 0.43с.

## Методика

Linux x86_64, AMD EPYC 9V74; доступная CPU quota — 8 ядер; DuckDB 2.0.0, Rust 1.99.1 release, strsim 0.11.1. Rust matcher однопоточный, DuckDB ограничен 4 потоками. Результаты одной среды, не прогноз для ноутбука.

По 3 повтора на каждый размер/сценарий, без скрытого warmup; ниже медианы в миллисекундах. Загрузка одинаковых исходных записей исключена из обоих времён. Включены нормализация, индекс/SQL materialization, retrieval, scoring, best/runner-up и формирование всех предложений. Rust дополнительно возвращает edit distance победителя; прежний SQL её не возвращал.

| Строк на сторону | Названия | Rust, мс | DuckDB, мс |
|---:|---|---:|---:|
| 1,000 | unique | 5.2 | 24.6 |
| 1,000 | ambiguous | 5.1 | 19.7 |
| 1,000 | dense | 31.4 | 29.1 |
| 10,000 | unique | 54.0 | 59.3 |
| 10,000 | ambiguous | 50.6 | 61.7 |
| 10,000 | dense | 342.0 | 171.3 |
| 100,000 | unique | 582.3 | 434.5 |
| 100,000 | ambiguous | 586.5 | 440.0 |
| 100,000 | dense | 3511.7 | 1434.0 |

- `unique`: отличающиеся названия, однозначный номер рецептуры.
- `ambiguous`: повторяющиеся названия у разных кодов; 4000 неоднозначных предложений на 100K.
- `dense`: блоки до 16 похожих кандидатов на каждую позицию; все 100K предложений неоднозначны.
- Во всех 27 сравнениях совпали From/To, score с допуском 1e-12 и ambiguous. Это проверка этих fixtures, не доказательство эквивалентности метрик на всех строках Unicode.
- Наивный перебор 100K × 100K не выполнялся ни в одном варианте.

Сначала Rust считал Levenshtein всех label-кандидатов, что дало около 8.5с на плотном наборе. Теперь расстояние вычисляется только для выбранного предложения. Для Join Lens его существующие ограничения коротких ключей и tie-breaking по edits сохранены.

## Память

Отдельные процессы с тем же тестовым бинарником, по одному движку, вся матрица 1K/10K/100K:

| Вариант | Пик RSS процесса |
|---|---:|
| Rust | 110936 KiB ≈108 MiB |
| DuckDB SQL | 598820 KiB ≈585 MiB |

На Linux измерено через `resource.getrusage(RUSAGE_CHILDREN).ru_maxrss` после одного дочернего процесса. Это RSS всего benchmark-процесса, включая исходные записи, результаты и аллокатор; для SQL также таблицы DuckDB. Это не вычитанная память одной функции. Тест с Rust не открывает соединение DuckDB. Результаты отдельного процесса также зависят от удержания памяти аллокатором между повторами. Замеры времени для таблицы выполнялись отдельно от замеров RSS.

## Воспроизведение

```bash
cargo test -p dwh-engine --release --lib benchmark_key_match -- --ignored --nocapture
```

Для отдельного движка: `DWH_MATCH_BENCH_ENGINE=rust` или `duckdb`. Пик RSS можно получить под `/usr/bin/time -v`, запустив уже собранный тестовый бинарник `target/release/deps/dwh_engine-<hash> --exact key_match_bench::benchmark_key_match --ignored --nocapture`; hash показывает Cargo. Не включайте компиляцию в замер памяти.

Сырые времена — `benchmark-results.csv`. Предыдущий SQL существует только в benchmark fixture, не в production path.
