# Проверки полного патча v2

База: `dwhforge/query`, `feature/mapping_tools`, `79111d547d1024f4dc48714e29f0d780fe71f79c`.
Этот патч полностью заменяет v1; применяется после его отката. Удалённый репозиторий не изменялся.

## Архитектура

- Один database-independent Rust matcher — `key_match.rs`; собственные версии Jaro/Levenshtein не реализуются, используется `strsim` 0.11.1 (MIT).
- Join Lens и полный KeyMap используют общие метрики, тип FuzzyPair и выбор best/runner-up, сохраняя явные различия политик для опечаток ключей и сравнения названий.
- `key_map_fuzzy.rs` только читает две query и валидирует входы; CPU matching работает вне mutex DuckDB.
- Нет `catalog_fuzzy.rs`, отдельной сущности Catalog, второго хранилища или дефолтов под демо в интерфейсе.
- Accept редактирует черновик существующей карты. Сохранение/конфликты/seed/source/ref остаются существующими путями. Сетка виртуализирована.
- Причины выбора Rust, его отставание по скорости и выигрыш в RSS описаны в `BENCHMARK.md`. Прежний SQL остался только как тестовая baseline.

## Что прошло

- `npm run build`: TypeScript и production bundle.
- Проверка реальной функции mergeKeyMapProposals: сохраняет ручные заполненные соответствия, заполняет пустые, пропускает ambiguous, не мутирует исходный массив.
- `cargo test -p dwh-pipeline`: **76** успешно.
- `cargo test -p dwh-engine --lib -- --test-threads=1`: **32** успешно, **1** benchmark по умолчанию ignored.
- Unit-проверки: many-to-one, альтернативный To, точные ничьи при gap=0, cutoff/gap, Unicode-нормализация, перестановка входных строк, переполненные общие token buckets, пустые входы, дубли/NULL/пробелы/слишком длинные поля/250001 строк, экранирование имён колонок, отсутствие мутаций workspace.
- Отдельно выполнен release benchmark: **27** сравнений Rust/SQL, результаты совпали на fixtures. Сырые времена прилагаются.
- `cargo clippy -p dwh-engine --lib` завершился: предупреждений в новых matcher-модулях нет; остаются существующие предупреждения других модулей (7 pipeline, 12 engine). Это не полностью warning-free repository.
- Host собран в release.
- Сгенерирован новый набор: 100000 продуктов/кодов с каждой стороны, 10000 продаж, 1M клиентов, остальные факты по генератору. Исходный KeyMap пуст.
- Сквозной native RPC: fuzzy → 100000 правильных предложений → mapped preview → export → **dbt build** → проверка фактического seed и опубликованной базы. Выполнены две сборки, затем повторный запуск на том же экспорте ещё с двумя сборками. Все проверки прошли.
- Последний RPC-прогон: matcher ~1.36с, preview ~5.09с, export ~0.46с, build ~5.04с и ~5.60с. Это маленькие факты, не нагрузочная оценка 200GB.
- Каждая сборка: **21 ресурс dbt**. Проверено 100000 соответствий, 10000 продаж, выручка 3255650.64, распределённая стоимость ~22498.5264636873, итоговый отбор 1 строка.

Версии: Linux x86_64; DuckDB 2.0.0; dbt-core 1.12.6; dbt-duckdb 1.11.1. Телеметрия dbt отключена в проверках и RPC-скрипте.

## Известное и непроверенное

- В v1 на повторном запуске возникало `WAL checkpoint iteration does not match the database file`. На выполненных прогонах v2 не воспроизвелось. Причина не локализована и **не считается исправленной этим рефакторингом**. При повторении сохраняйте DB+WAL+логи; тест ничего не удаляет и не чинит.
- 200GB / сотни миллионов строк не генерировались: этот прогон выполняется у вас.
- GUI на 100K карте не проверялся интерактивно; собран UI и протестированы backend/merge. Пройдите ручной сценарий README.
- Живая публикация в PostgreSQL не запускалась; маршрут выбирается в приложении, verifier PG поддерживает.
- Windows/macOS, внешний USB SSD, dbt 2.x не проверены.
- Fuzzy проверен на технический масштаб. Синтетические названия не доказывают качество на реальных неоднозначных справочниках. Ограниченный retrieval может пропускать совпадения; одинаковые распространённые названия без редких признаков могут остаться без предложений.
- Verifier проверяет покрытие, суммы и предикаты, а не полное построчное равенство всей бизнесовой логики.
